# Developing Desktop Buddy

How to run Buddy from source, test it, configure it and release it. What Buddy does for the people using it is in
[GUIDE.md](GUIDE.md).

## Run from source

```bash
npm install
npm run setup   # fetches the pinned agent-desktop CLI into bin/
npm start
```

The first time you start it with `npm start`, Buddy adds **Desktop Buddy** to the Start menu and the desktop
and turns on **Start with Windows**, so you never need the terminal again. Both live in the tray menu afterwards
("Start with Windows" checkbox, "Recreate shortcuts"). Launching Buddy while it is already running opens the Ask
bubble. The icon is generated by `node scripts/make-icon.js` into `assets/`.

On first launch Buddy asks how to think: paste an API key (Anthropic, OpenAI, OpenRouter or Gemini are recognised;
for DeepSeek or a model on your PC, choose it in Settings first). Keys are stored encrypted with Windows DPAPI
(Electron `safeStorage`), one per provider. `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `OPENROUTER_API_KEY`,
`GEMINI_API_KEY` and `DEEPSEEK_API_KEY` override the stored key for their provider.

`npm run smoke -- notepad` checks the agent-desktop bridge without calling the model.

`npm test` runs the unit tests (`test/*.test.js`, Node's built-in runner; no model calls, nothing on the desktop is
touched). They pin down the rules that matter most: approvals, slips and their scopes, the approval queue, the
read-only command path, the mode and task-state tables, the island's state, the provider adapters and what models can
do, the file tools' places and the PowerShell guard, undo, keys bound to their address, sessions from AI apps, history
trimming, the SVG sanitizer and escaping in explainers, the reading view, spoken text, and never overwriting a
document. CI (`.github/workflows/ci.yml`) runs `npm run check`, `npm test` and `npm audit` on Windows for every push
to `main` and every pull request, and, beside them, `npm run e2e -- --no-voice` (every check below but voice; a failed
run keeps `e2e-out/` as a download for a week).

`npm run e2e` runs the real app end to end, each check in a separate test copy with its own data folder (your Buddy,
settings and files are left alone): **markerStartup** (generated captures, parallel preparation, cancellation,
late-window ownership and timeout recovery, all on the still), **markerLive** (the native overlay: a stroke drawn and
undone through its test commands, toolbar buttons, the picture for the question carrying the stroke, Cancel and a quick
click closing it, drawing speed, and the still taking over when the overlay can't start), **markerRender** (generated sample content, standard/high-DPI pixels, long strokes,
pointer cancellation, Undo and composed-image marks; no real mouse input or desktop capture), **annotations** (all five drawing types, safe labels, task ownership, a real
guided step with its expected result, interruption and focus/anchor cleanup), **context** (a test-owned chart window supplies a real screenshot and accessibility
refs; turning screenshots off removes images from the next request), **conversation** (streaming and mid-answer
corrections), **files** (a scripted model asks for a file; the approval card is clicked; the file
is made, listed in Activity and undone; another window can't answer the card), **tasks**, **settings** (including a
key that must stay with its server), **controls** (every Settings control clicked or typed into as a person would:
each must be saved, shown, and take effect, such as the island's colour, the bubble's language, a plate's theme, a
registered shortcut or the Agents rules; Start with Windows, adding Buddy to AI apps and the links that open the
browser are left out because they'd change the PC), **explainer** (a plate opened in Light, switched to Dark while open), **voice**, **bridge** (an AI app's calls over its own pipe: answered
with the token, refused without), **language** (the windows in Spanish, every Settings page read for English left behind, then switched to English
while open),
**connections** (a stand-in service with real OAuth on this PC: the
bubble's offer, signing in, a tool call through the approval card), **lessons** (a lesson played in a test-owned window with no model, a missing control
told, a shared file round-tripped), **restore** (Buddy quit and restarted on one data folder: tasks and the bubble's
conversation come back, closing a task forgets it), and **firstrun** (a plain test copy must leave your
startup entries and shortcuts as they were). Any check whose copy logged a refused mode or task-state change fails.
`npm run e2e -- --exe "<path to Desktop Buddy.exe>"` runs them against a built or installed copy. `npm run e2e -- --interactive` adds the marker (drawn on the live screen) and the approval
clicks below (it moves the mouse). `--no-voice` is for a PC without the voice models: it leaves out the voice check
and the settings check's language part. Screenshots and logs go to `e2e-out/`.

`npm run eval -- --provider openai --model <id>` runs the model check (seven sample Buddy tasks, scored) from the
command line, with the key from the provider's usual variable; Settings › AI & privacy › **Check this model** runs the
same with your saved key.

For stricter checks over recorded Excel and Edge windows, list the six workflows without making a model call:
`npm run eval -- --set workflows --list`. They cover opening and verifying a dialog, correcting a target,
continuing after a tab change, website search, a missing button and an unopened dialog.

Run a model against them with `npm run eval -- --provider <provider> --model <id> --set workflows --json workflow-results.json`.
This uses that provider's API and can cost money. Each result includes every request and correction, tool calls,
time to first reply text, time to first guidance tool result, total time and token usage. The saved-key runner accepts
the same options. Unknown case IDs and set names fail before any model call.

Workflow replay accepts only controls in the current recorded screen and requires a newly observed expected result
before a guide can finish. It never reads or operates your desktop. The older `made-up` and `real` sets remain
route checks; their scores do not prove completion. Recorded replay does not measure drawing smoothness, actual
mouse use or time spent waiting for a person. Its English recovery checks are explicit heuristics: review the saved
transcript alongside the score before judging model quality. `npm test` checks the runner with scripted replies;
those passes are not a live model score.

To apply corrected checks to saved replies without another API call, use
`npm run eval -- --set workflows --rescore workflow-results.json --json workflow-rescored.json`.
Choose a new output file: existing files cannot be overwritten. Transport failures and cancellations remain failures.

Two smaller sets: `--set sight` (eight made-up screens with nothing the accessibility tree names; a case passes
when the spot Buddy points at is inside the target's box) and `--set show-me` (the tour's **Show me** on three
recorded windows; a case passes when Buddy points at one named control with a caption, does nothing, and keeps its
reply to a sentence or two).

`--set blender` builds in Blender: a cabin from scratch, opening Blender then a snowman, and changing a table. It runs on
a stand-in Blender that keeps the scene (`src/evals.js` `blenderScene`); a check reads what was built (parts present,
standing on the ground or on each other, lit, the camera placed, nothing of the user's deleted). Add `--live-blender`
to build in the Blender open on your PC instead (Blender 5.1+ with Blender Lab's MCP add-on running): nothing is asked
there, so use a scene you don't mind changing.
The saved-key runner uses a temporary runtime profile. It reads the saved key and the OS-encrypted key metadata
needed to unlock it, without rewriting Buddy's saved key or copying unrelated profile data.

`BUDDY_APPROVAL_TEST=cycle npm start` checks, with a real mouse click (the pointer moves; keep your hands off the
mouse), that an approval card takes a click and that the keyboard goes back to your app afterwards. Cases: `plain`,
`guide`, `cycle` and `twoasks` (see `main.js`). It guards a Windows quirk: switching the bubble to "can't take focus"
after it had been closed and reopened left it deaf to every click, so approval cards and Stop stopped working. The
bubble now never switches; it steps back and hands the keyboard to your window instead.

`npm run measure:idle` starts a separate copy of Buddy and reports its CPU use and memory while idle, per process
type (keep the mouse still; add `-- -Budget 1.0` or `-- -MemoryMB 200` to fail above a limit). Buddy should sit near
1% of one core: the overlay draws only while the pointer moves, and the cursor check slows to 20 times a second once
the mouse is still. Judge memory by its private column (`-MemoryMB` does): working set counts the libraries every
process shares once per process. On 2026-11-17 it read 2-5% of one core and about 190 MB private (ROADMAP.md 4.6);
CI fails above 250 MB.

`npm run check` type-checks every main-process module (TypeScript reading the JSDoc types; nothing is compiled). It
holds three rules in place:

- **Approvals.** Anything that clicks, types, opens an app or moves a window runs only through `desktop.perform()`,
  which accepts only a single-use slip that `approvals.js` issues after the user says yes. Read-only commands go
  through `desktop.observe()`, which refuses everything else.
- **One mode at a time.** `main.js` tracks what Buddy is doing as a `Mode` (idle, marking, reading-marks, listening,
  working). Every change goes through `enter()`, which allows only the moves in `NEXT` and logs any other as
  `refused-mode-change` in `timing.log`. `NEXT` and the busy messages are typed `Record<Mode, …>`, so a new mode
  doesn't pass the check until both cover it.
- **Coordinates.** agent-desktop works in physical pixels and Electron in DIPs; `geometry.js` gives each its own
  type, and `main.js` converts between them only through `toPhysicalPoint`, `toPhysicalRect` and `toDipRect`.

## Configuration

These environment variables override Settings (useful for development):

| Variable | Default | Purpose |
|---|---|---|
| `BUDDY_HOTKEY` | `Control+Alt+B` | Global shortcut ([Electron accelerator](https://www.electronjs.org/docs/latest/api/accelerator)) |
| `BUDDY_EXPLAIN_HOTKEY` | `Control+Alt+E` | Explain what's under the cursor |
| `BUDDY_MARK_HOTKEY` | `Control+Alt+M` | Highlight things to ask about |
| `BUDDY_TALK_HOTKEY` | `Control+Alt+T` | Talk to Buddy (not Ctrl+Alt+V, which is Paste Special in Office) |
| `BUDDY_DICTATE_HOTKEY` | `Control+Alt+D` | Dictate into the app you're in |
| `BUDDY_VOICE` | `0` | Supertonic voice, `0`–`9` |
| `BUDDY_GPU` | unset | `1` turns GPU acceleration back on. It's off by default because on some dual-GPU laptops the GPU compositor leaves Buddy's transparent windows (the island, the pointer) blank |
| `BUDDY_MODEL` | Settings | The model, for whichever provider is chosen |
| `BUDDY_EFFORT` | `medium` | `low` is snappier, `high` is more careful |
| `AGENT_DESKTOP_BIN` | `bin/agent-desktop.exe` | CLI to drive (a local agent-desktop build, for instance) |
| `BUDDY_DOCUMENTS_DIR` | `Documents\Buddy` | Buddy's working folder |
| `BUDDY_ENGINE` | unset | `sdk` runs Anthropic conversations on the Claude Agent SDK (needs the SDK, which installers leave out) |

## Languages

Buddy's windows show their words through `src/i18n.js` (main process) and `src/ui/strings.js` (pages). The English is
the key: `t("Thinking…")`, `t("Typed {n} words", { n })` in code (`tr` in tasks.js, where `t` is a task), `N("…")`
where words are defined in a table and translated where they're shown, and `data-t` / `data-t-attrs="title"` on
fixed words in a page. Words a script changes on the fly are translated in the script, not marked in the page.

Translations are `src/locales/<code>.json`. `test/strings.test.js` fails when a marked string has no translation,
placeholders differ, or a translation is left over. To add a language: add it to `LANGUAGES` in i18n.js, list what
it needs with `node test/strings-scan.js`, and write `src/locales/<code>.json`. Have a native speaker read it.

## How it fits together

```
hotkey ─► main.js ── remembers the window you were in (list-windows, is_focused)
            │
            ├─► island.html   status pill, task chips and their live previews
            ├─► bubble.html   prompt, replies, approval card, mic
            ├─► overlay.html  one click-through window per display: the pointer and its caption
            ├─► tasks.js      task windows (task.html), each with its own Brain
            ├─► voice.js      voice.html (hidden: microphone, end-of-speech detection, playback)
            │      └─► speech.js  child process: Moonshine + Supertonic on sherpa-onnx (models.js fetches and checks them)
            ├─► brain.js      the tool loop: look · screenshot · point_at · guide_steps · act · list_windows · …
            │      ├─► providers.js  Anthropic, OpenAI (Responses), and Chat Completions for the rest; what models can do
            │      ├─► pc-tools.js   files, PowerShell, web pages (places, the PowerShell guard, hidden secrets)
            │      │     └─► wall.ps1  each command inside a Windows AppContainer: the working folder only, no network
            │      └─► desktop.js ─► agent-desktop CLI (snapshot -i --compact --include-bounds, click, set-value…)
            ├─► approval-queue.js  the approval card's queue; approvals.js issues the single-use slips
            ├─► island-state.js    what the island says, worked out from what Buddy is doing
            ├─► activity.js   what Buddy changed this week, and undo
            └─► bridge.js     the named pipe AI apps reach Buddy through
                   ├─► mcp-server.js  the MCP server the AI apps start (on Buddy's own exe); starts Buddy if it's closed
                   ├─► app-sessions.js  one Brain per AI app session, calls in turn
                   └─► ai-apps.js     adds Buddy to Claude Code, the Claude app, Codex, Gemini CLI, Cursor, VS Code…
```

The speech engine is a plain Node child process (Electron run as Node), not an Electron utility process: Windows
runs utility processes at background priority on the efficiency cores, which made both models about twice as slow.
Every speech request has a deadline, so an engine that stops answering is restarted instead of leaving Buddy stuck.
Only the hidden voice page may open the microphone, and only while Buddy is listening. Dev check without speakers:
`BUDDY_VOICE_TEST="Click the Formulas tab." npm start` (muted round trip; add `BUDDY_VOICE_TEST_MIC=1` to try the mic).

Why these models: on this laptop they understand speech about 5× faster than Whisper base.en at the same accuracy,
speak as fast or faster than Kokoro, use about a third of the memory, and none of them depend on eSpeak NG (GPL-3.0),
which Kokoro's phonemizer embeds. Licences are in [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md); the Supertonic
voice comes with use restrictions (no impersonating people without consent, among others) that pass on to you.

Element bounds stay in `brain.js` for the pointer; Claude sees a compact text tree with refs.
agent-desktop reports physical pixels; `main.js` converts them to DIPs with `screen.screenToDipRect`.

Explainers are model-written HTML, so they render with JavaScript disabled, a CSP of `default-src 'none'`,
script/iframe/meta/link elements stripped, and a dedicated session that cancels every non-`file:`/`data:` request.
Each one is saved under `%APPDATA%/desktop-buddy/explainers/`.

Requests to Anthropic use `fallbacks: "default"` (beta `server-side-fallback-2026-07-01`), so a declined request is
retried on Anthropic's recommended fallback model rather than failing outright.

## Release

1. Bump `version` in `package.json`, add the release to `CHANGELOG.md`, and commit.
2. Push a matching tag: `git tag v0.2.1 && git push origin v0.2.1`.
3. `.github/workflows/release.yml` fetches the pinned agent-desktop, runs the checks and tests, builds the native
   helpers (`npm run native`: Mark's overlay and the commands' wall launcher, into `build/native`, shipped as
   `resources\native`; see `src/native.js`), builds the installer on Windows, and uploads it with `latest.yml` to a
   **draft** release `v0.2.1`. `npm run dist` and `npm run dist:dir` build the helpers too; after `dist:dir`,
   `node scripts/check-packed-helper.mjs` checks they're in the app and match its sources, and
   `npm run e2e -- --exe "dist/win-unpacked/Desktop Buddy.exe" markerLive` checks the app runs the shipped overlay
   and compiles nothing.
4. Review the draft, add notes, and publish it. Installed copies only see published releases.
5. Check that `https://github.com/donlapidos/desktop-buddy/releases/latest/download/latest.yml` names the new version.
   Installed copies check about a minute after they start, download in the background, and install when Buddy quits
   or the user picks **Restart to update** in the tray.

Updating was checked end to end for 0.2.0 → 0.2.1: an installed 0.2.0 found 0.2.1 a minute after starting,
downloaded it and verified its checksum; that installer, run silently as the updater runs it, updated the install in
place, and the updated copy checked the new repository. To repeat it without touching an everyday copy, start the
installed `Desktop Buddy.exe` with `--user-data-dir=<empty folder>` and watch that folder's `timing.log` for
`update-ready`.

Copies of 0.2.0 installed from the old home (`donlapidos/agent-desktop`) look for updates there. That repository
carries the same 0.2.1 release so they move over once; after that they update from here.

`npm run dist` builds the same installer locally into `dist/`; `npm run dist:dir` builds just the unpacked app, which
can't update itself.

Buddy drives the [agent-desktop](https://github.com/vercel-labs/agent-desktop) CLI at the version pinned in
`package.json` (`agentDesktop`: version and SHA-256 of upstream's Windows release). `npm run setup` downloads it into
`bin/`, checks the checksum, and does nothing if the pinned version is already there. To move to a newer
agent-desktop, update both fields from that release's `checksums.txt`, run `npm run setup`, and run `npm test` and
`npm run e2e`.

### Signing

`release.yml` signs only when the repository has the secrets `WIN_CSC_LINK` (the certificate as a base64-encoded
`.pfx`) and `WIN_CSC_KEY_PASSWORD`. It hands them to electron-builder as `CSC_LINK` and `CSC_KEY_PASSWORD`, which
signs Buddy's exe, the uninstaller and the installer during the build and only then writes `latest.yml` and the
blockmap, so the SHA-512 and size that installed copies check are the signed installer's. Without the secrets the
build is unsigned, exactly as before. With them, a step checks the installer's signature and fails the run if it
isn't valid.

**Before buying a certificate:** since June 2023 every publicly trusted code-signing certificate keeps its private key
on a hardware token or in the CA's cloud, so most can't be exported as a `.pfx`. Certum's open-source certificate
lives on a card or in SimplySign (their cloud app, which needs a code from a phone to sign), so it can't be fed to
`WIN_CSC_LINK` in GitHub Actions. With it, signing happens on the owner's PC: sign the installer from the draft with
`signtool`, then rebuild `latest.yml` (`sha512` is the base64 SHA-512 of the signed file, `size` its byte count, in
both the `files` entry and the top-level `sha512`) and the `.blockmap`, and upload all three over the draft's copies.
That needs a small script that isn't written yet. A service that signs from CI, such as Azure Artifact Signing
(electron-builder's `win.azureSignOptions`), avoids that, if the owner is eligible for it.

## Owner handover: shipping 0.5.0

Everything the agent couldn't do. Run the commands from the repository folder.

### 1. Record the demo (30 seconds)

The rehearsed script for both launch clips is `docs/DEMO.md`. The steps below are the general way to record and add one.

1. Open a small Excel sheet (a short budget works well). Close anything private.
2. Start the Windows screen recorder (**Win+Shift+R**, or Snipping Tool › Record) around Excel and Buddy's island.
3. Press **Ctrl+Alt+B**, ask for something with three or four steps ("How do I turn this into a table and sort by
   amount?"), and follow Buddy's pointer. Stop when Buddy says you're done. Aim for 30 seconds.
4. Save it as `docs/media/buddy-demo.mp4`, then make the README's moving picture (GitHub can't play an mp4 in a
   README) with ffmpeg (`winget install Gyan.FFmpeg`):

   ```powershell
   ffmpeg -i docs\media\buddy-demo.mp4 -vf "fps=12,scale=720:-1:flags=lanczos,split[a][b];[a]palettegen[p];[b][p]paletteuse" docs\media\buddy-demo.gif
   ```

   Keep the gif under about 10 MB (lower `fps` or `scale` if not).
5. Take two screenshots with **Win+Shift+S**: Buddy's pointer and caption on a control, saved as
   `docs/media/pointer.png`, and Mark with two numbered strokes, saved as `docs/media/mark.png`.
6. In `README.md`, uncomment the demo line and replace the two "Picture coming soon" cells with
   `<img src="docs/media/pointer.png" alt="…" width="300">` and the same for `mark.png`. `docs/index.html` already
   points at `media/buddy-demo.mp4`.

### 2. The certificate (optional)

Read **Before buying a certificate** above first. Certum's open-source code-signing certificate was the earlier
choice; check its current price and whether it comes as a card or SimplySign. If you get one that exports as `.pfx`
(or switch to a CI signing service), add the secrets:

```powershell
$b64 = [Convert]::ToBase64String([IO.File]::ReadAllBytes('C:\path\to\certificate.pfx'))
$b64 | gh secret set WIN_CSC_LINK --repo donlapidos/desktop-buddy
gh secret set WIN_CSC_KEY_PASSWORD --repo donlapidos/desktop-buddy   # paste the password when asked
```

Releases ship unsigned until then, as 0.3.0 to 0.5.0 did; the website and release notes say how to get past
Windows' "protected your PC" warning.

### 3. Tag and publish

After this branch is merged to `main` and `main` is pulled:

```powershell
git checkout main
git pull
git tag v0.5.0
git push origin v0.5.0
```

The Release workflow builds the installer into a **draft** release v0.5.0 whose notes only say its name. Watch it with
`gh run watch`, then publish it with the 0.5.0 notes from `CHANGELOG.md` (saved to a file, with the line on getting past
Windows' warning at the end), in one go:

```powershell
gh release edit v0.5.0 --notes-file <notes file> --draft=false --latest
```

Check that `https://github.com/donlapidos/desktop-buddy/releases/latest/download/latest.yml` says `version: 0.5.0`:
installed copies offer the update from then on.

### 4. Turn on the website

Done on 2026-11-19: the site is at https://donlapidos.github.io/Desktop-Buddy/ and updates itself from `main`. For a
new fork:

GitHub › the repository › **Settings › Pages** › Source: **Deploy from a branch**, Branch: **main**, folder
**/docs**, Save. Or:

```powershell
gh api -X POST repos/donlapidos/desktop-buddy/pages -f "source[branch]=main" -f "source[path]=/docs"
```

The site appears at `https://donlapidos.github.io/desktop-buddy/` within a few minutes. Add it to the repository's
About box as the website.

### 5. Submit to winget

After the release is published, follow [packaging/winget/README.md](../packaging/winget/README.md): fill in the
installer's SHA-256, validate, then

```powershell
wingetcreate submit --token <github token> packaging\winget\manifests\d\donlapidos\DesktopBuddy\0.4.0
```
